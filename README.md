# tree-sitter-cromo

A [tree-sitter](https://tree-sitter.github.io) grammar for the Cromo programming language (`.cro` files), with the queries an editor needs: highlights, brackets, indents, outline, text objects and runnables. The capture names follow the conventions of Zed.

## Layout

- `grammar.js`: the grammar.
- `src/scanner.c`: the external scanner. Cromo has no `;`: the scanner gives the newline that ends a statement, and leaves it out before a `{`, an `else`, a `catch` or a `finally` on the next line.
- `src/parser.c` and the rest of `src/`: generated by `tree-sitter generate`, and kept in the repository because editors compile the parser from them.
- `queries/`: `highlights.scm`, `brackets.scm`, `indents.scm`, `outline.scm`, `textobjects.scm`, `runnables.scm`.
- `test/corpus/`: the tests of `tree-sitter test`.

## Working on the grammar

```sh
tree-sitter generate --js-runtime native   # or without the flag, with node on the PATH
tree-sitter test
tree-sitter parse path/to/file.cro
tree-sitter query queries/highlights.scm path/to/file.cro
```

## Notes on the grammar

- A declaration `Type name` and an expression start in the same way, and so do `list<i32>` and a comparison, a lambda `[x](i32 a) { }` and a list `[x]`. The grammar declares these conflicts and the parser follows both readings until one fails; when both hold, the one with type arguments wins, as in the compiler.
- `>>` and `>>=` are a `>` followed at once by `>` or `>=`, so that `list<list<i32>>` closes two lists of type arguments.
- The built-in types (`i32`, `string`, `list`...) and the built-in functions (`println`, `assert`...) are plain names in the grammar: `highlights.scm` tells them apart.
- The runnables are tagged `cromo-main` for `main` and `cromo-test` for a function with `[[test]]`, whose name is in the capture `test_name` (`$ZED_CUSTOM_test_name` in a task of Zed).
